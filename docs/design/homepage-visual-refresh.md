# Blueline Lease homepage visual refresh

Design and implementation plan · November 16, 2026 · Scope: public homepage `/`

The approved direction gives the current homepage a stronger visual rhythm. Use a quiet light surface, dark navy typography, the existing blue-and-red document marks, a friendly 3D Spotter in the hero, two photographic role cards, compact feature icons, and a worked sample report with a small Spotter peeking from its edge. Keep the review recognizable from the first click through the report.

## Responsive and accessible presentation

- **Desktop, 1024 px and wider.** Keep the existing desktop nav breakpoint and `max-w-6xl` (72 rem) content width. Use the current approximately 3:2 hero grid. Art can fill the second column up to about 440 CSS px wide, with a natural aspect ratio and a stable reserved box. Keep the role cards in an equal-width pair with about 16–24 px between them. Start at roughly 180–220 px tall and allow growth for text. Limit the sample peek to about one quarter of the panel width and keep it within the section’s outer bounds.
- **Tablet, 768–1023 px.** Keep the mobile menu. Continue the two-column hero only while the copy, both CTAs, motto, and full Spotter silhouette fit. Use a smaller art column or stack the hero before anything crowds. Keep cards side by side when both text blocks wrap comfortably. Preserve the checklist’s existing two-column label layout when space permits. Move the peek inward or reduce it before it can collide with report text.
- **Phone, below 768 px.** Keep copy and actions before artwork in DOM and reading order. Stack hero and art, and let CTA labels wrap or stack at narrow widths. Stack cards below the existing `sm` boundary (640 px), or sooner if contrast and text-fit checks require it. Keep the face and lease marks visible at phone scale. Let the sample excerpt reflow without truncation. Move the peek to a lower corner or omit it at narrow widths if it would overlap content. Let checklist items become a single column when needed. Allow sections and cards to grow in height.
- **Layout checks.** Start with staging’s 24 px page gutters and 40 px at `sm`. Reduce only a homepage-local gutter if 320 px reflow requires it. Test 320, 375/390, 640, 768, 1024, and 1440 px, plus 200% zoom and 320 CSS px reflow. Keep the hero H1 and primary action easy to find before art, and keep card text and focus outlines unclipped.
- **Semantics.** Preserve landmarks, one H1, heading order, and the targets `#main`, `#how-it-works`, `#sample-report`, and `#features` with existing skip and anchor behavior. Keep the section targets programmatically focusable and verify the skip link reaches the main content. Keep standard links and buttons in DOM order, minimum existing 44 px target heights, visible focus, and reference text selectable. Use empty alt text for redundant artwork and background photos, and hide decorative icons from assistive technology. If art conveys information beyond the adjacent text, expose the equivalent in HTML. Keep the mascot still and honor reduced motion.
- **Contrast.** Meet the project’s [WCAG 2.1 AA target](https://www.w3.org/TR/WCAG21/). Use at least 4.5:1 for normal text, 3:1 for large text, and 3:1 for meaningful UI boundaries and indicators against adjacent colors. Check the actual rendered combinations in every crop and hover/focus state. Computed sRGB ratios for the verified tokens are Navy Ink on Paper 12.74:1, Navy on Paper 10.31:1, and Paper on Navy Ink 12.74:1 for a solid card scrim. Red Ink on Paper is 4.91:1, but on Paper Deep it is 4.34:1 and fails for normal text. Signal Red on Paper is 3.56:1 and on Paper Deep 3.14:1, below the normal-text threshold. Signal Red on Navy is 2.90:1, so place the ring against a solid contrasting underlay or use a dual ring on photos or dark backgrounds. Prefer navy text or Paper-backed Red Ink badges when a red small label would fail. Ensure severity and emphasis remain understandable without color.
- **Manual access pass.** Use keyboard and a screen reader to check the skip link, responsive menu including Escape, CTA and sample-anchor landings, card names and order, both sample destinations, and both role buttons in intake. Check high zoom, simulated image failure, and increased text spacing. Use automated checks as a complement to these checks.

## Performance and stability

- Use `next/image` with intrinsic dimensions or an aspect-ratio container and accurate `sizes` for the hero, each photo, and the peek. Use responsive AVIF or WebP and keep visible text in the HTML. Lazy-load below-fold images. Give high priority only to the hero artwork if a measured trace shows it is the relevant LCP resource. Preserve the logo’s existing treatment.
- Working transfer budgets for the selected responsive variants are up to 150 KiB for the mobile hero and 250 KiB for desktop, 100 KiB per role photo, and 50 KiB for the peek. Measure the actual requested variants. A first-view mobile target for all new images together is at most 350 KiB. Return to crops and compression if the initial composition exceeds it.
- Compare before and after at the same viewport and network settings using cold, repeated Lighthouse or DevTools runs and a network waterfall. Record mobile LCP, CLS, and requested bytes. Target CLS at or below 0.1 with no visible shifts from image load, and LCP at or below 2.5 s where the baseline already meets it. If the baseline is slower, investigate repeatable regression before handing off. Keep the UI usable if image requests fail. Use no video, 3D runtime, third-party asset requests, or new client bundle for decorative UI.

## Implementation sequence and staging control

1. **Confirm and plan.** Check the working tree and project instructions, intended Preview SHA and protections, and its relationship to current `origin/main`. Record the verified tokens, route and copy inventory, and baseline desktop/mobile screenshots and performance. Inspect asset usage and availability. Write a short plan with touched components, asset files, approved reference adaptations, and smoke checks before editing.
2. **Isolate.** Branch from the owner-approved Preview baseline, or current `origin/main` after confirming it matches, in a dedicated feature branch such as `feat/homepage-visual-refresh`. Carry these planning files into the branch if needed. Keep the implementation in homepage markup, styles, and new visual assets. Maintain the existing route entry points, shared navigation, analysis, scoring, documents, authentication, data, and report contracts. No dependency, service, migration, or environment settings change is needed.
3. **Integrate in small commits.** Add optimized artwork and the hero treatment, then the two sample-link cards and worked excerpt, then compact coverage icons and responsive adjustments. Use the prepared assets or the existing text surfaces while assets are pending. Keep the real intake, sample routes, and existing copy functional after each commit.
4. **Verify locally.** Run `npm run lint`, `npm run typecheck`, `npm test`, `npm run build`, and `npm run smoke` without `--live`. Use the landing-copy, sample-report, and review-role tests as focused regression checks. For browser review with synthetic documents, use `npm run build:fixtures` and then `npm run start:fixtures -- --port 3100` in the isolated checkout. The fixture build replaces its `.next` output and does not exercise hosted auth or saved reviews. Run normal and fixture builds sequentially. Use only assets and synthetic documents authorized for this work.
5. **Publish to a protected Preview only.** Before pushing the feature branch, verify with the repo’s deployment setup that it creates a Vercel Preview and will leave the production branch, domains, protected settings, and Preview shared alias alone. Record the baseline and candidate immutable Preview URLs and SHAs. Confirm the target is Preview in GitHub/Vercel after the build and verify the deployed homepage and both sample pages. Use the documented staging project with synthetic accounts and leases for any authorized hosted auth or persistence smoke. If isolation or credentials cannot be confirmed, do the local fixture smoke and report what remains unverified.
6. **Hand off for review.** Provide desktop and mobile before/after screenshots, Preview URL and commit, measured color and performance evidence, flow and accessibility checks, art provenance, deviations, and any remaining gaps. Leave the feature branch unmerged. Production deployment, promotion, or a merge to `main` requires the owner’s explicit approval.
