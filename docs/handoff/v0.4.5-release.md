# v0.4.5 authentication fix

Owner report and diagnosis: November 19, 2026. [Ticket 44](../../.scratch/lease-review/issues/44-signup-passwords-and-existing-accounts.md) records the requested behavior. This patch follows the approved local → staging → PR review → main → production process.

## Behavior

Signup now requires matching passwords, checked on the server before contacting Supabase. Password fields have independent Show/Hide controls. Sign-in keeps one field; signup and reset have two.

The confirmation screen no longer implies that a fresh email was necessarily sent. It points existing users to sign-in or password reset instead of leaving them waiting for another signup code. These options appear for everyone, so the response does not reveal whether an address has an account.

## Diagnosis and checks

The two reported addresses were already confirmed accounts. A fresh production sign-in email arrived for each address; both links opened their account pages, and both diagnostic sessions were signed out. No existing password or account data was changed. Supabase documents its duplicate-signup privacy behavior in the [JavaScript signup reference](https://supabase.com/docs/reference/javascript/auth-signup).

Before the fix, three signup regressions and four password-control tests failed. The updated authentication suite passes 29 tests. Local lint, route type generation, typecheck, all 671 tests, the production build and both deterministic role smokes passed. The smoke checks ran through Node's tsx import because the sandbox blocked the tsx CLI's local IPC pipe; the build completed outside the restricted sandbox. The published [GitHub release](https://github.com/ThisisMendez/blueline/releases/tag/v0.4.5) will record the exact Preview head, separate Standards and Spec reviews, required CI and the verified production commit. Do not infer that deployment has completed from this source document alone.

## Limits and recovery

The live diagnostic verifies email-link login for both reported existing accounts. It does not verify either owner's private password or guarantee delivery to every mailbox. No new production account, reset of an owner's password, database migration, sender change or model change is included. Fresh signup and recovery have boundary regression coverage; any additional live end-to-end checks must be recorded separately.

If production verification fails, restore the previous working Vercel deployment and use a reviewed revert to reconcile main. Keep required checks and account-confirmation controls enabled.
